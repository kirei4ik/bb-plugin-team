# Общий бюджет эпика — проектирование

Статус: первый срез реализован для Issue #3: ручная привязка и finite gate в
ResourceControl, утверждаемая ревизия scope, управление в панели ресурсов и
`bb team budget --epic`.
Автономного планирования нет. Инструкция — в skills/team/SKILL.md.

Текущие границы: привязку нельзя очистить или переключить на builtin; смена
эпика сохраняет его историю. Управление доступно только вручную вне agent CLI.
Сохранение не отправляет сообщение и не запрашивает dispatch/recheck; продолжение
остаётся отдельным действием. Исторический расход до активации не приписывается
эпику. Изменение бюджета требует завершения outstanding reservations и ходов.
Задачи вне эпика отображаются в диагностике и удерживаются на dispatch/admit.
Конфликт записи состояния проверяется сравнением сохранённой версии JSON в
транзакции существующей БД; устаревший допуск удерживается. Если после записи
решения в Beads возник конфликт Team, решение остаётся в истории, но разрешение
не сохраняется: перечитать обе стороны перед повтором.
Основание: PR #4 и ResourceControl на c6cd372, локальная проверка bd 1.3.1.

## Контракт Beads

Задачи, критерии, тип и parent остаются в Beads. `bd create --parent` в 1.3.1
не возвращает parent; `bd show` и `bd list --all --parent` возвращают явный
parent. Идентификатор с точкой не доказывает родство. Метки родителя наследуются,
поэтому создание через Team допускает ровно одну метку bb-team, текущей команды.
Проверка создания не защищает от последующих внешних изменений.

## Минимальный сценарий

Человек выбирает открытый эпик текущей команды и конечный лимит admission units.
Капитан работает на самом эпике; исполнители — на его непосредственных дочерних
задачах; помощники наследуют задачу владельца. Две дочерние задачи расходуют один
бюджет вместе с капитаном. При исчерпании новые автоматические ходы ждут решения,
активный ход заканчивается. Создание третьей задачи ничего не обнуляет.
Вложенные эпики, автономное планирование, денежные лимиты и новый планировщик
исключены из первого среза.

## Данные и миграция

Расширить существующий ResourceState: активная привязка эпика и словарь бюджетов
по неизменяемому Beads epicId внутри projectId/team. Бюджет хранит finite limit,
время активации и revision; попытка ResourceAttempt получает immutable epicId.
Это технический учёт, не копия задач. При смене сессии, модели, активного эпика,
завершении или удалении дочерней задачи старые записи сохраняются. Повторная
активация того же epicId использует прежний расход. Новый child не создаёт
новый epic budget. Отсутствие полей означает прежний режим пакетов; старые задачи
не получают эпик автоматически. Builtin отказывает в активации эпика явно.

Активация требует отсутствия незавершённых reservations/ходов команды и явного
решения человека. Проверять открытые пакеты и привязки: посторонние задачи
удерживать с диагностикой, не переписывать им parent. Исторический расход до
активации не приписывать эпикам по сегодняшней изменяемой иерархии. Отображать
границу учёта явно; автоматическое создание эпиков запрещено.

## Допуск и учёт

Расширить ResourceControl, не вводить второй admission hook. В существующей
serial-операции перед append читать текущую привязку и авторитетные данные
Beads. Проверять открытый epic, единственную командную метку и точное parent
задачи; для капитана допустима сама задача эпика. Helper проходит ту же проверку
через ownerThreadId/taskId, включая вложенных помощников. Неизвестный taskId,
несколько parent, недоступный Beads, чужой/закрытый эпик дают wait с причиной.
Проверку выполнять также перед dispatch, до status=in-progress/deliverPackage;
допуск повторяет её непосредственно перед резервированием расхода.

Проверка лимита и запись reservation составляют одну атомарную операцию в
существующей БД ResourceControl. Существующая serial-очередь достаточна для
одного экземпляра; при нескольких писателях нужна транзакция с revision/CAS и
повторной проверкой лимита, без ожидания Beads внутри синхронной транзакции.
Гарантия scope ограничена последним прочитанным состоянием Beads: общей
транзакции между Beads и Team нет. Изменение parent после чтения не позволяет
обнулить уже списанный epicId; следующий admit снова проверяет иерархию.

Одна новая reservation = одна единица. Все роли, retries, review rework и
fallback проходят этот путь. Reentry одной reservation и replay событий не
списывают повторно. Отменённые и неопределённые reservations сохраняют расход.
Review return сам по себе не вызывает модель: общий бюджет списывает следующий
admit; существующий дополнительный package return counter сохраняется отдельно.
Сумма attempts с epicId определяет used; новую задачу/сессию нельзя использовать
для восстановления лимита. Изменяемую текущую иерархию не использовать для
пересчёта прошлого расхода.

Общий gate проверяется и для userControl капитана: прежнее исключение package
cap не должно обходить epic cap. После исчерпания управление бюджетом доступно
через детерминированный UI/CLI без запуска модели. Ручной BB Send-now обходит
hooks: учитывать наблюдаемый запуск с сохранённым epicId, показывать превышение,
не обещать запрет этого штатного обхода. Если атрибуция наблюдаемого события
неизвестна, удерживать следующие admits до явного решения; не игнорировать его.

## Управление и диагностика

Расширить существующую панель ресурсов и CLI бюджета. Показывать название и ID
эпика, его критерии из Beads, limit/used/remaining, границу учёта, причину hold и
неатрибутированные задачи. Изменение лимита: человек, expectedLimit/expectedUsed,
revision, причина в выбранном трекере перед сохранением разрешения. Если запись
в трекер не удалась — лимит не повышать; частичный результат диагностировать.
Повтор после неопределённого результата требует перечитать состояние.
Снятие/смена epic binding также требует человека и не очищает расход.
Изменение бюджета не снимает quota hold, scope guard или failure hold.

## Проверки перед включением

- Реальный путь без AI: выбрать существующий epic, назначить finite limit,
  прочитать две дочерние задачи; fake BB допускает капитана/helper/исполнителя
  до общего лимита, затем UI/CLI показывает конкретную причину и решение.
- Новый child, ротация, смена модели, повторная активация и restart ResourceControl
  сохраняют used. Конкурентные admits не превышают limit; replay/reentry не
  удваивают расход; потерянные/отменённые reservations не возвращают единицы.
- Проверить чужие/неизвестные parent, внешнее переподчинение, закрытый epic,
  несколько командных меток, Beads unavailable и builtin отказ без fallback.
- Проверить quota/failure hold вместе с исчерпанием, userControl без обхода
  общего gate, неизменность старых команд без привязки и scope-lock dispatch.
- Перед автономностью нужны реализация этих защит и полный набор проверок.
  Admission units ограничивают число ходов, а не запросы/токены внутри хода.

## Обязательные условия до автономного цикла

Защита ревизии scope реализована. Остальные условия ниже ещё не дают права
включать автономный цикл.

- Реализовано: человек утверждает ревизию scope эпика: требования, критерии приёмки и
  принадлежность команде. Team хранит технический SHA256-отпечаток ревизии;
  содержимое остаётся в Beads. Изменение требований или критериев извне
  удерживает следующий автоматический ход, пока человек явно не утвердит новую
  ревизию. Капитан и helpers не переутверждают scope и не повышают свой лимит.
- Проверка ревизии нужна перед dispatch и admit, с проверкой конфликтов между
  чтением Beads и записью допуска. Общей транзакции между системами нет: нельзя
  обещать защиту от внешнего изменения после последнего чтения. Уже списанные
  попытки сохраняют первоначальную атрибуцию и ревизию.
- Один разрешённый запуск цикла получает конечные общий бюджет, срок и предел
  повторов без подтверждённого прогресса. Счётчики сохраняются для того же эпика
  при рестарте, новом ребёнке, возврате, замене модели или сессии. Исчерпание
  приводит к удержанию до решения человека, а не к созданию свежей цели.
- Продолжение использует существующую очередь BB. Ошибка, неизвестный исход,
  недоступность трекера, смена scope или квота исключают слепой повтор
  spawn/send. Нет второго планировщика и отдельного наблюдателя-LLM.
- Допуски ходов не ограничивают внутренние запросы одного хода. Перед включением
  требуется проверить доступные штатные ограничения BB/провайдера на длительность
  и работу внутри хода. Пока они не выбраны и не проверены, не объявлять цикл
  защищённым денежным или полным вычислительным лимитом.

Приёмка следующей итерации должна воспроизводить изменение критериев и parent
во время ожидания, отказ агенту самостоятельно утвердить scope, конфликт
ревизий, исчерпание после рестарта/нового ребёнка, повтор событий и отсутствие
прогресса. При каждом удержании нужен конкретный путь решения через существующие
UI/CLI, без вызова модели для объяснения собственного запрета. Проверка сначала
через SDK fake и реальный Beads, затем изолированный живой BB; реальные модели
и сам автономный цикл требуют отдельно определённого конечного сценария.


## Граница ручного управления ресурсами

SDK 0.6.132 различает подтверждённого вызывающего plugin и обычного client, но
браузер, CLI и агент для RPC — один и тот же client. Поле входа «я пользователь»
не доказывает согласие. Поэтому записи ресурсов через RPC отклоняются для
plugin callers и удерживаются, пока в проекте есть выполняемый ход, pending
операция/взаимодействие или активная фоновая работа. Проверяется полный список
включая скрытые треды; ошибка или обрезанный список запрещает изменение.
Неактивная errored-сессия допускает ручное восстановление. Существующие
reserved/running допуска проверяются атомарно в ResourceControl перед записью.
Ручной CLI имеет ту же проверку; подлинное текущее пользовательское обсуждение
с lead сохраняет прежнее исключение только для лимита пакета.

Это защита от обычного активного агента, не доказательство личности человека:
произвольный код на хосте с тем же локальным доступом к BB остаётся доверенным.
Нельзя обещать полную изоляцию RPC без более сильного контракта ядра BB.
