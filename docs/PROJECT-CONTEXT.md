# Контекст для продолжения разработки Team

Это карта принятых решений, а не список задач. Актуальный бэклог и состояние
работы находятся в Beads. Для начала читать [карту исходников](STRUCTURE.md),
задачу и её последнюю передачу. Для окончания — [порядок закрытия](SESSION-CLOSE.md).

## Основные договорённости

- Выбранный трекер — единственный источник задач, критериев, зависимостей,
  статусов, решений и результатов. Beads по умолчанию; встроенный трекер остаётся
  отдельным вариантом. Ошибка Beads не переключает проект на второй список.
- Выбор трекера общий для проекта. Team хранит технические связи задачи, роли,
  треда и окружения; содержимое задачи не дублируется в его KV.
- Роль постоянна, тред — сменяемая сессия, в том числе у руководителя.
  Иерархия руководитель → исполнители → помощники сохранена.
- Передача использует структурированный checkpoint, а не последний ответ.
  Сохраняются та же задача, среда и незакоммиченная работа. Переключение —
  между операциями; неопределённый spawn/send не повторяется вслепую.
- На роль — один выполняемый пакет, остальные стоят в очереди. Руководитель
  делегирует, проверяет доказательства и принимает/возвращает результат.
  Наличие текста отчёта само по себе не доказывает качество.
- По решению пользователя самоприёмка собственных задач руководителем пока
  разрешена. Общий серверный запрет не вводить без нового решения. Исходные
  ограничения конкретной задачи сохраняются при передаче сессии.
- Счётчик контекста, расход задачи и остаток аккаунта — разные величины.
  Автоматическая ротация от 80% требует точных данных; приблизительные
  показания не дают права запускать её. Есть явная передача через checkpoint.
- Расход пакета не сбрасывается сменой модели или сессии. Новый пакет имеет
  отдельный лимит; общий счётчик запусков команды — статистика.
  Активная работа завершается; новые запуски удерживаются до решения.
  Встроенный BB Send-now — явное ручное исключение: плагин не может запретить
  этот обход своих dispatch hooks и не должен обещать обратное.
- Источник квоты определяется подключением к сервису. Один OpenRouter-ключ
  может использоваться разными агентами. Другие ключи/агенты не доказывают
  независимость аккаунтов. Секреты остаются на рабочем хосте; неизвестный
  источник не подменяется ключом другого сотрудника.
- Квоты проверяются перед ходами с кешем до трёх минут. За один ход агент
  может сделать много запросов; запас не гарантирует отсутствие исчерпания.
  Отложенное продолжение использует штатную очередь BB и снова проверяет
  условия. Дополнительного планировщика и наблюдателя-LLM нет.

Ручное возобновление Codex после quota failure проверяет свежие штатные
`system.usageLimits` на хосте сессии: все окна должны иметь запас выше
порога. Неизвестные данные и переопределения `CODEX_*`, `OPENAI_*`, `HOME`,
`XDG_*` в окружении BB не подтверждают тот же источник квоты и удерживают
запуск. Проверка рассчитана на штатный Codex и управляемое BB окружение;
произвольные обёртки и внешняя смена credentials требуют отдельной проверки.
Снятие относится только к упавшим запросам той же сессии/задачи, сохраняет
расход и остальные блокировки. Чужая блокировка того же источника квоты
вызывает явный отказ с откатом снятия собственной блокировки. Оно не создаёт повторный ход: ручной retry
выполняется отдельно через очередь BB. Автоматического сброса по часам нет.

## Границы дальнейшей работы

ИИ-генерация промптов отложена по выбору пользователя до подходящего публичного
text-only API BB. Не заменять её скрытым агентом с доступом к хосту. Наличие
такого API нужно проверять по текущему SDK при возобновлении соответствующей
задачи, а не считать старый spike вечным ограничением.

Сначала использовать существующие возможности BB и публичного SDK. Не создавать
второй трекер/планировщик и не обещать экономию без измерений. Исследование —
целевой проход; проверки — по изменению, полный необходимый набор перед приёмкой.
Пользователь предпочитает короткие отчёты, простые деревья и обоснованные
самостоятельные решения; спорные продуктовые границы и расходы уточнять.

Предпочтения по моделям не заменяют проверку доступности, квот и действующего
разрешения на запуск. Не повышать расходы и не включать платные резервы молча.
Само обсуждение/планирование не разрешает реализацию.

## Применение и публикация

Разработка ведётся в отдельном worktree. Продолжая задачу после смены сессии,
сохранить её существующую среду, а не создавать чистую копию ветки. База Beads —
в каноническом checkout. `bd init` в execution-worktree запрещён.

Различать исходники в worktree, основной checkout, установленную сборку и
публичный релиз. Локальное применение не означает push или публикацию.
Версия в package.json не идентифицирует все локальные доработки: фиксировать
Git-коммит и фактическую проверку. Push, теги и marketplace PR требуют отдельного
разрешения. Конкретные хосты, каталоги, разрешения и результаты последней сессии
должны быть в передаче Beads, а не выводиться из этого общего документа.

## Восстановление привязки сотрудника

При создании/подключении роли Team закрепляет `active-session` до освобождения
начального сообщения. Устаревший указатель на архивный тред не означает, что
роль отсутствует: сначала проверяются существующие помеченные сессии.
Панель показывает нарушение привязки отдельно от квот и бюджета. Однозначная
сессия в прежнем окружении восстанавливается явным действием и остаётся на
паузе; восстановление не вызывает модель и не обнуляет ограничения. Несколько
кандидатов, незавершённая замена или неподтверждённая среда запрещают угадывать.
Если живой сессии нет, её создание остаётся отдельным действием с запуском
модели. Архивные треды автоматически не разархивируются.


Лимиты запусков назначаются пакетам работ, а не проекту/команде. Общий счётчик
сохраняется как статистика; `teamStarts` — устаревший совместимый вход без gate.
Расход одной taskId общий для помощников, моделей и сессий. Новый пакет независим.
Панель меняет лимит выбранного открытого пакета через `packageBudget` с проверкой
expectedLimit/expectedUsed и записью основания в трекер. Ошибки, квоты и частичные
передачи не снимаются изменением бюджета. Значения по умолчанию действуют на
новые пакеты, прежние лимиты и расход сохраняются при миграции.


Решения о лимитах пакетов можно согласовывать в чате руководителя. Канонический
lead получает подлинное сообщение пользователя даже при исчерпании package cap
(расход учитывается; прочие guards сохраняются). `bb team budget <id>` читает
текущие расход/предел; запись требует limit/expected-limit/expected-used/reason.
Для lead проверяется текущий user-control admission; автоходам и исполнителям
повышение не разрешено. Семантика согласия — ответственность lead, не regex по
сообщению. Повышение через UI уведомляет простаивающего lead, если очередьпуста;
наличие очереди не порождает дублирующий ввод. Названия работ обязательны в
сообщениях пользователю; ID сами по себе не являются объяснением.


## Общий бюджет эпика

Для команд с явно выбранным Beads-эпиком действует дополнительный конечный
лимит допусков всех ролей: капитана, исполнителей и помощников. Техническая
привязка и immutable epicId попыток сохраняются в существующем ResourceControl;
иерархия и критерии остаются в Beads. Новая дочерняя задача, модель или сессия
не сбрасывает расход. Команды без эпика сохраняют прежние лимиты пакетов.
Управление общим лимитом — ручное, через панель или CLI вне agent thread;
исключение package cap для пользовательского разговора не обходит epic cap.
Сохранение бюджета не отправляет сообщения и не запрашивает новый dispatch.
Детали контракта и ограничения — в [EPIC-BUDGET.md](EPIC-BUDGET.md) и skills/team.
Автономный цикл капитана этим изменением не включается.


Scope эпика закрепляется SHA256-ревизией его идентичности, требований и критериев.
Пользователь видит требования перед явным утверждением; CLI передаёт показанный
scopeRevision. Внешнее изменение удерживает новые допуски; расход сохраняется.
Заметки о ходе работы, решения по бюджету и статусы в hash не включаются.
Legacy epic budget без ревизии требует явного утверждения, старые команды без
эпика работают по-прежнему. Ручные записи ресурсов через RPC требуют отсутствия
активных ходов/фона и reserved/running допуска; SDK не различает browser/CLI/agent
client, поэтому это операционный guard, а не изоляция от произвольного кода хоста.
